# R9 — Tokenizer/preprocess memcpy storm in the hot path

> x86→Arm/Graviton migration template · kind: `probe` · confidence: low · expected gain (estimate): 1.1–1.6×

## Anti-pattern

perf report attributes a large share of cycles (>= 15%) to memcpy/memmove/memset — the classic signature of per-token string slicing, repeated buffer reallocation, or copy-per-request serialization in tokenizer and preprocessing code.

## Before → after

```python
# per-token slicing: every token reallocates and copies
out = b""
for tok in tokens:
    out += table[tok].encode()        # O(n^2) copies
return out
```

```python
# pre-size once, write into a view: no reallocation, no copy storm
parts = [table[tok].encode() for tok in tokens]
buf = bytearray(sum(map(len, parts)))
view, off = memoryview(buf), 0
for p in parts:
    view[off:off + len(p)] = p
    off += len(p)
return bytes(buf)
```

## Fix

The only LLM-creative rule: the planner drafts a batch/zero-copy rewrite suggestion for the identified call site (memoryview/pre-allocated buffers/batched tokenization). Deterministic fallback emits the hot-symbol evidence and generic zero-copy guidance; any drafted patch must pass the reproduce gate like every other fix.
