# R13 — Serving overhead dominates kernel time (two-instrument divergence)

> x86→Arm/Graviton migration template · kind: `probe` · confidence: high · expected gain (estimate): 1–1×

## Anti-pattern

llama-bench timings exclude tokenization and sampling (verified caveat in crawl/clean/sdk_llamacpp.md), so Armsmith runs BOTH instruments on the same workload: llama-bench for kernel-time tokens/sec and hyperfine for end-to-end wall time. When end-to-end exceeds kernel time by more than 15%, the pipeline — not the kernels — is the bottleneck, and kernel tuning cannot deliver the expected wins.

## Fix

Diagnostic rule: quantifies the kernel vs pipeline split and redirects optimization to the serving layer (batched tokenization, prompt caching, streaming, server reuse instead of process-per-request). Both instruments' self-reported stats are cross-checked against their raw samples before the split is trusted.

## Expected gain

1–1× — Diagnostic: no direct patch gain is claimed (range pinned to 1.0x); the value is redirected effort, quantified from two real instruments.

> Estimates are for planning order only. Only Armsmith's reproduce gate (median-of-N · MAD noise band · output-hash equality) can claim a result.
